# Mobile relief and document intake

Implement the agreed mobile critique on `feature/mobile-relief-intake`, based on
the existing build-14 follow-up. Preserve the Family Journal design.

## Acceptance

- PDF/image sharing from iOS and Android enters the authenticated family's
  durable upload queue; cancellation, login and retry cannot silently discard it.
- The private family email address is available from native intake and family;
  copy/share actions use the configured server domain, never an invented alias.
- Interrupted uploads retry with an idempotency key and remain scoped to their
  original family. Files are removed only after a durable state transition.
- Device registration, revocation, notification routing and server delivery are
  connected. Notifications contain no private document/task titles. Scheduled
  delivery reports failures and retries; "enabled" requires server registration.
- Today includes today's appointments, incomplete processing and actionable
  documents before offering a narrowly worded calm state. Completion has Undo.
- The first scan is reachable before optional member setup. Confirmation shows
  actual retained tasks/dates. Chat starters are short labels with precise prompts.
- Family task handoff distinguishes assignment from an actual acceptance.
- Local lint, typecheck, unit/integration tests and build; native checks and
  simulator inspection; migration dry run, PR and green CI. A physical-device
  share/push check and deployment configuration are reported separately.

No implementation can promise literal perpetual availability. The experience
must accurately expose saved, processing, retryable and unavailable states.

## Implemented behavior and rollout

- iOS uses a checked-in native share controller generated by
  `plugins/with-ordilo-share.cjs`. Each delivery gets its own directory and an
  atomic commit marker in `group.com.ordilo.app`. The extension is named Ordilo.
  It uses Apple's supported completion API, with no UIApplication responder hack.
  It confirms **saved on this iPhone**, then asks the user to open Ordilo for
  processing. This is a deliberate platform limitation, not background upload.
  The app stages and acknowledges individual deliveries; an arrival during an
  import cannot be erased by acknowledging the previous one. Android uses Expo's
  incoming intent integration. PDF/photo only, up to ten attachments per share.
- Existing unscoped drafts from older versions require explicit assignment to
  the current family. Existing server documents are checked for family ownership.
- Push registration is serialized with logout and uses bounded network waits.
  Tokens are service-only. Membership and current subject state are checked again
  before sending; stale daily reminders and completed documents are withdrawn.
- The existing GitHub background runner now requests document and notification
  processing every five minutes and fails visibly on HTTP errors. GitHub schedule
  timing is best-effort. Daily Vercel jobs remain a fallback without requiring a
  higher-frequency Vercel plan. Quiet hours are 20:00–08:00 in the device timezone.

Release order:
1. Apply migration 0074 before releasing the native build. It is idempotent.
   Historical migrations 0005/0017 also correct their six-argument function grants,
   allowing a fresh database bootstrap; no production schema change in those fixes.
2. Deploy the API and configure `JOBS_RUNNER_SECRET` (also the repository secret),
   `VERCEL_DEPLOYMENT_URL` repository variable, and Vercel `CRON_SECRET` as applicable.
3. Receiving email requires `INBOUND_EMAIL_DOMAIN`, `RESEND_API_KEY`,
   `RESEND_WEBHOOK_SECRET`, a verified receiving domain/MX, and the signed Resend
   receiving webhook pointing to `/api/email/inbound`. Native shows an unavailable
   state when configuration is absent. No real email was sent during local tests.
4. Build a new EAS native binary so app-group entitlements and the extension are
   provisioned. The runtime fingerprint protects older installed binaries from an
   incompatible OTA. Verify APNs/FCM credentials; `EXPO_ACCESS_TOKEN` is supported
   when Expo push access-token security is enabled.
5. Before production rollout, check real-device PDF/photo sharing from Files,
   Mail and Photos, offline/relaunch, two equal filenames, VoiceOver/Larger Text,
   and delivery to a second family member's physical device. Also build Android.

## Validation evidence

- Migration chain bootstrapped in isolated local Supabase on ports 58321/58322;
  migration 0074 dry-run, application and repeated application succeeded.
- `supabase/tests/mobile_relief.sql` passed: RLS isolation, explicit acceptance,
  upload uniqueness, notification deduplication, reassignment invalidation,
  exclusive lease and exhausted-lease recovery, all rolled back.
- Live local API: synthetic school PDF uploaded concurrently twice and replayed;
  all responses returned the same document. Server OCR/analysis reached `analyzed`
  with one page. Missing receiving configuration correctly returned no address.
- Native iOS simulator compilation succeeded both unsigned and locally signed,
  including the custom share extension. Mobile unit checks include durable inbox
  acknowledgment, interrupted manifests, unsafe paths, retry and real outcomes.
- Interactive simulator verification was interrupted by the Mac lock. It is not
  claimed complete. Physical device push/share and Android runtime remain release
  gates; no production migration, email, app submission or deployment was done.
- Final local checks: web lint/typecheck, 203 Vitest files / 2,940 tests and
  production Next.js build passed; mobile lint/typecheck and 37 Jest suites /
  360 tests passed. The two transient web note-flow failures from an earlier
  heavily concurrent run passed individually and in the complete final run.
